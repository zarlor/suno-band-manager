# Memory System for Mac — the v2 Sanctum

**Sanctum location:** `{project-root}/_bmad/_memory/band-manager-sidecar/`

> **Preserved divergence (documented):** Mac's sanctum lives under the
> **double-underscore** `_memory` parent (the `{project-root}/_bmad/_memory/...`
> path above), NOT the v2-default single-underscore `memory/{skill}/` parent. The
> path is load-bearing — portable sync and the reconcile tooling depend on it. Do
> not "fix" it to the v2 default.

## Core Principle

Tokens are expensive, and the always-loaded layer is paid on every rebirth. Only
the curated essence loads on wake; the raw material lives one tier down and is
pulled on demand. Mac remembers the owner's musical preferences and current
state, not every conversation.

## The Two-Tier Model — sessions → MEMORY

The single biggest change in the v2 sanctum: raw session narrative and curated
state are **split into two tiers**.

- **`sessions/YYYY-MM-DD.md` (raw, NOT loaded on rebirth)** — every session
  appends its raw "what happened today" narrative here: the running Current/Prior
  Work blocks, the play-by-play of a workshop, the detail behind a publish. This
  is the durable record; nothing is lost. It is *not* read on activation because
  it grows without bound.
- **`MEMORY.md` (curated, loaded on every rebirth)** — the distilled "what the
  owner is DOING and prefers right now" layer. Each session's raw notes are
  curated *up* into this file, kept tight (target <~200 lines). It carries the
  preferences, exclusions, active band profiles, current/pending work, module
  state, and the derived catalog sections.

The discipline: **append raw to `sessions/` every session; distill up into
`MEMORY.md` and keep it tight.** See `references/save-memory.md` for the save
flow that enacts this.

## Loaded / On-Demand / Not-Loaded Tiers

**The full loaded / on-demand / not-loaded tier map is owned canonically by the
sanctum's `INDEX.md`** (seeded from `assets/INDEX-template.md`). That map is the
single source of truth for which files load on rebirth, which load on demand, and
which never load. Do not duplicate the full table here — read it from `INDEX.md`.

What this doc fixes in place (the parts that explain *why* the tiers exist):

- **Loaded on rebirth (always) — exactly 7 files, in this order:**
  `access-boundaries.md` (FIRST, before any file op) → `INDEX.md` → `MEMORY.md` →
  `CREED.md` (slim core; carries the Package Assembly Rule core) → `PERSONA.md` →
  `BOND.md` → `CAPABILITIES.md`. This matches `pre-activate.py`'s
  `{sanctum_load_order}` and `references/activation.md` step 4. `MEMORY.md` is kept
  tight (the two-tier model below is what keeps the always-loaded layer bounded).
- **Loaded on demand:** the creed shards (`creed-disciplines.md`,
  `creed-workshop-capture.md`, `creed-package-assembly.md`) and owner-taught
  `capabilities/` prompts — pulled when their trigger context arises. The shard
  trigger table lives in `CREED.md` / `references/capabilities.md` / `INDEX.md`.
- **Not loaded on rebirth:** the raw `sessions/YYYY-MM-DD.md` logs, `chronology.md`,
  `patterns.md`, `creed-incident-log.md`, `_collection_*.txt` — see `INDEX.md` for
  the full list and the why-not-loaded rationale.

**PULSE.md** is the maintenance-wake routine (not a knowledge file). On an
autonomous/maintenance wake, Mac loads `PULSE.md` and runs its narrow,
report-and-stage maintenance sweep — it never edits creative content (a Law 3
hard line). See `references/activation.md` "Maintenance / Pulse Wake".

## The Preserved Bespoke Machinery

The v2 sanctum keeps Mac's own superior machinery rather than collapsing it into
the generic v2 defaults:

- **`access-boundaries.md`** stays a standalone, loaded-first Dominion file — it
  is stronger and more specific than a generic CREED-Dominion section. `CREED.md`
  points at it.
- **`BOND.md` stays thin.** Mac's owner-model is richer than a single collapsed
  BOND: it is split across `docs/voice-context-{user}.md` (creative identity),
  `docs/mac-preferences.md` (behavioral preferences), and sidecar `patterns.md`
  (learned musical patterns). BOND.md orients to those traveling sources; it does
  not duplicate them.
- **`patterns.md`, `chronology.md`, `_collection_*.txt`** are preserved organic /
  working files, indexed from `INDEX.md`.
- **Derived catalog sections** (`Recently Published`, `Catalog Status`) live in
  `MEMORY.md` between `<!-- derived:recently-published:start/end -->` and
  `<!-- derived:catalog-status:start/end -->` marker pairs, regenerated by
  `scripts/regenerate-index-sections.py`.

When a new organic file is created, add a row to `INDEX.md` — an unlisted file is
a lost file.

## The Traveling Companion Files (in `docs/`, not the sanctum)

These live in `docs/` so they travel in portable sync (the sanctum itself is
per-machine and does NOT travel). They are loaded on activation but live outside
the sanctum.

### `docs/voice-context-{username}.md` — User Voice & Context

**Load on activation** (before greeting). The user's durable creative identity —
the "slow memory" that persists across sessions and machines.

**Contains:**
- **Who I Am** — Personal history, creative background, identity, what drives them
- **How I Write** — Form, themes, emotional drivers, stylistic evolution, influences
- **How to Work With Me** — Communication preferences, what to avoid, what works best
- **Creative Catalog** — Songs created, albums, key production notes, playlist structure
- **Suno Preferences** — Tier, models, voice, default sliders, exclusions, personal sonic preferences. Production learnings (metatag behavior, prompt engineering, model quirks) belong in skill reference docs and sidecar `patterns.md`, not here.
- **Session History** — Condensed timeline of sessions and milestones
- **Current Creative State** — Active WIPs, directions being explored, threads to pick up

**Multi-user:** One file per user, named by normalized username (lowercase,
spaces→hyphens): `voice-context-alex.md`, `voice-context-bob-smith.md`. Mac
writes only to the current user's file.

**Update discipline:** Only when genuinely new durable context emerges — new
personal history, new creative work, significant preference changes, production
breakthroughs. Not after every minor exchange.

**Relationship to the sanctum:** the voice file is the "slow memory" (who the
user IS); `MEMORY.md` is the "fast memory" (what the user is DOING right now).
Both load on activation.

**Size management:** If the file exceeds ~2000 lines, offer to compact: summarize
older session history, consolidate redundant entries, but preserve personal/voice
sections in full.

**Companion Files table:** The voice file should include a **Companion Files —
Load On Demand** section near the top. This table indexes satellite documents
that extend the voice file with depth that doesn't live in every session's
context:

| File | What | When to load |
|------|------|-------------|
| `docs/example-deep-dive.md` | Detailed context on [topic] | When discussing [trigger] |

When Mac creates a satellite document during a session, add a reference entry at
creation time. At session-end save, audit for new `docs/` files not yet in the
table. Each entry needs: file path, one-line description, and a when-to-load
trigger.

### `docs/mac-preferences.md` — User-Specific Mac Behavioral Preferences (Portable)

**Load on activation** (after the voice file). This file carries durable
user-specific behavioral preferences for how Mac communicates and shapes
responses — communication style, pacing rules, framing rules, the user's
articulated meta-conversation preferences. It answers a different question than
the voice file: not "who is this user creatively?" but "how does this user want
me to talk with them?"

**Why it lives in `docs/` and travels in portable sync:** behavioral preferences
need to travel across machines. Per-machine agent memory caches (e.g. Claude
Code's `$HOME/.claude/projects/...` memory directory) do NOT travel in the
portable sync archive — preferences saved there only apply on the machine where
they were articulated. Writing them to `docs/mac-preferences.md` makes them
travel with every other shared artifact.

**Contains (per-entry):** title + one-line description; why it matters (the
correction that produced the rule); how to apply it; cross-references where useful.

**When to write:** whenever the user articulates a durable behavioral correction
about how Mac should communicate. Append the new entry in the SAME turn the
correction lands — don't defer to save-memory time (per `creed.md` "Sync at the
point of change"). The drift window between an event and the save is unacceptable;
the session may be interrupted at any point.

**What does NOT belong here:**
- Suno platform knowledge (metatag behavior, model quirks, prompt strategies) → `src/skills/*/references/*.md` upstream in the module
- Musical/creative preferences (genre tendencies, vocal preferences, slider sweet spots) → sidecar `patterns.md` or voice file
- Band/catalog policies → `docs/band-profiles/*.yaml` or voice file
- Ephemeral session state (current work, pending threads) → sanctum `MEMORY.md`

**Relationship to per-machine agent memory:** harness-local memory systems
(Claude Code, Codex CLI) are appropriate for **truly machine-local** content
(per-machine env vars, auth tokens, machine-specific workflow notes), NOT for
behavioral preferences that should follow the user across machines.

## Memory Persistence Strategy

### Write-Through (Immediate Persistence)

Persist immediately when:
1. **User preferences change** — tier, default mode, exclusions
2. **First-run setup completes** — all initial preferences (write as you go — see `references/init.md`)
3. **User requests save** — explicit `[SM] - Save Memory` capability

### Checkpoint (Periodic Persistence)

Update periodically after:
- Completing a create-song or refine-song flow
- The user switches interaction modes or updates preferences mid-session
- `MEMORY.md` approaches its ~200-line curated bound (distill / push detail down to `sessions/`)

### Save Flow (two-tier)

Memory is updated via the `[SM] - Save Memory` capability, which (see
`references/save-memory.md` for the full protocol):
1. Captures any unsaved creative fragments to WIP files first
2. Appends the session's raw narrative to `sessions/YYYY-MM-DD.md`
3. Curates/distills the live state up into `MEMORY.md` (keeping it tight)
4. Regenerates the derived sections (`regenerate-index-sections.py` → `MEMORY.md`) + genre-coverage
5. Updates `INDEX.md` when a new organic file was created
6. Checkpoints `patterns.md` / `chronology.md` if needed
7. Validates with `validate-sidecar.py`

## Write Discipline

**Handoff checkpoint:** Before writing to any sanctum file, surface what will be
written, get user confirmation, then write. This matters especially for
`patterns.md` (personal preferences) — the user controls what gets stored as a
"pattern" about them.

Before writing, ask:

1. **Is this worth remembering?** If no → skip.
2. **What's the minimum that captures this?** Condense to essence. No fluff.
3. **Which tier?**
   - Raw session detail → `sessions/YYYY-MM-DD.md`
   - Distilled live state, preferences, current/pending work → `MEMORY.md`
   - Musical quirks, recurring feedback patterns → `patterns.md`
   - Significant timeline events → `chronology.md`
4. **Does this need an `INDEX.md` row?** If a new organic file was created — yes.

## Memory Maintenance

Regularly (every few sessions, or when `MEMORY.md` nears its line bound):
1. **Distill** — push raw detail down to `sessions/`, keep `MEMORY.md` tight
2. **Prune outdated content** — `check-memory-health.py` flags files over their bounds
3. **Consolidate patterns** — merge similar musical preference entries
4. **Update chronology** — archive significant past events

`scripts/check-memory-health.py` reports the bounds: `MEMORY.md` is line-bounded
(~200 lines — long derived-catalog lines are fine), `patterns.md` / `chronology.md`
have generous char ceilings (organic reference files, not loaded on rebirth),
and `sessions/` files are raw and never flagged.

## State Checkpoints (Context Compaction Resilience)

After each complete create-song or refine-song cycle, write a lightweight state
checkpoint to `MEMORY.md` "Current Work" containing:
- Current song: title, style prompt (first 100 chars), model, band profile
- Active mode (Demo/Studio/Jam)
- Refinement round count (if refining)

If context compaction drops earlier conversation, Mac recovers essential state
from `MEMORY.md`; the full play-by-play remains in `sessions/`.

## First Run

If the sanctum doesn't exist, `scripts/init-sanctum.py` scaffolds it from the
`assets/` templates, then `references/init.md` runs the conversational First
Breath calibration. See `references/init.md`.

## Post-Unpack Reconciliation (Cross-Machine Sync)

When a portable sync archive is unpacked on a receiving machine, the sanctum's
curated `MEMORY.md` still reflects the receiving machine's prior state — even
though the newly-arrived files may contain updates the narrative should
integrate. If this drift isn't reconciled, Mac presents outdated framing in the
very next interaction.

**The protocol is mandatory, not optional:**

1. `unpack-portable.{sh,ps1}` invokes `reconcile-sidecar.py` automatically after extraction and prints a report.
2. Re-run reconcile explicitly — `python3 scripts/reconcile-sidecar.py "{project-root}" --format json` (or `uv run` if deps are missing) — and walk every entry in `newer_files` (files modified more recently than the sanctum store — the newest of `MEMORY.md` / `INDEX.md`) plus every validator finding with the user via the Handoff Checkpoint Pattern.
3. Integrate approved changes: append the raw arrival detail to the relevant `sessions/` file as needed, distill the live state up into `MEMORY.md`.
4. Run `regenerate-index-sections.py` to refresh the derived sections in `MEMORY.md`.
5. Only then proceed into the normal activation flow (greeting, menu, etc.).

**Rationale:** the pre-pack validator gates sync on the source machine. Without a
post-unpack reconciliation gate, the freshly-arrived file state and the receiving
machine's sanctum narrative drift apart with every round trip. Reconciliation is
the agent's job — the script only produces the punch list.
